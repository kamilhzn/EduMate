## 1. RAG（检索增强生成）基础理论

### 1.1 什么是 RAG

RAG（Retrieval-Augmented Generation，检索增强生成）是一种结合**信息检索**与**大语言模型生成**的技术架构。它解决了 LLM 的三大核心问题：

| 问题 | RAG 的解决方案 |
|------|---------------|
| **知识时效性**：LLM 训练数据有截止日期 | 从外部知识库实时检索最新文档 |
| **幻觉问题**：LLM 可能编造不存在的事实 | 答案必须基于检索到的真实文档内容 |
| **领域知识不足**：通用 LLM 缺乏垂直领域知识 | 上传专业课程资料作为私有知识库 |

### 1.2 RAG 的标准流程

```
用户提问 → Query 改写 → 检索（Retrieve）→ 上下文拼接 → 增强生成（Generate）→ 返回答案
```

1. **Retrieve（检索）**：从知识库中找到与问题最相关的文档片段
2. **Augment（增强）**：将检索结果作为上下文注入 Prompt
3. **Generate（生成）**：LLM 基于增强后的 Prompt 生成答案

### 1.3 EduMate 中的 RAG 实现

EduMate 的 RAG 流程在 `StreamingChatService.buildContext()` 中编排：

```
Query 改写（口语→检索优化）
  → 混合检索（向量 + 关键词 + 图谱，三路并行）
  → RRF 融合排序
  → 拼接上下文 + 对话历史 + System Prompt
  → LLM 生成答案
```

### 1.4 面试要点

- RAG 与微调（Fine-tuning）的区别：RAG 不修改模型参数，成本低、可解释性强、知识可实时更新
- RAG 的常见挑战：检索质量、上下文窗口限制、多跳推理、检索与生成的衔接
- 进阶方向：Agentic RAG（让 Agent 自主决定何时检索、检索什么）、Graph RAG（结合知识图谱）

## 2. Spring Boot 3.4.5 框架

### 2.1 核心概念

Spring Boot 是基于 Spring Framework 的**约定优于配置**（Convention over Configuration）的微框架，核心特性：

- **自动配置（Auto-Configuration）**：根据 classpath 中的依赖自动配置 Bean
- **起步依赖（Starter Dependencies）**：一站式引入相关依赖（如 `spring-boot-starter-web`）
- **内嵌服务器**：内置 Tomcat/Jetty/Undertow，无需外部部署
- **Actuator**：生产级监控端点（健康检查、指标、环境信息）

### 2.2 IoC 与依赖注入

**IoC（Inversion of Control，控制反转）**：将对象的创建和管理权交给 Spring 容器，而非由开发者手动 new。

**DI（Dependency Injection，依赖注入）**：Spring 通过构造函数、Setter 或字段注入的方式将依赖传递给对象。

EduMate 中统一使用**构造函数注入**（推荐方式）：

```java
// edumate-admin/.../ChatController.java
public ChatController(ChatModel chatModel,
                      StreamingChatService streamingChatService,
                      IntentClassifierService intentClassifierService,
                      RefusalGuardService refusalGuardService,
                      ChatSessionService chatSessionService) {
    this.chatModel = chatModel;
    // ...
}
```

### 2.3 常用注解

| 注解 | 作用 | EduMate 使用场景 |
|------|------|-----------------|
| `@SpringBootApplication` | 启动类标记（含 @Configuration + @EnableAutoConfiguration + @ComponentScan） | `EduMateApplication` |
| `@RestController` | REST 控制器（= @Controller + @ResponseBody） | 所有 Controller 类 |
| `@Service` | 业务逻辑层标记 | 所有 Service 类 |
| `@Configuration` | 配置类标记 | DashScopeConfig、QdrantConfig 等 |
| `@Bean` | 方法返回值注册为 Spring Bean | 各 Config 类中的 Bean 定义方法 |
| `@Value` | 注入配置文件属性 | 注入 API Key、端口等配置 |
| `@PostConstruct` | Bean 初始化后执行 | QdrantConfig 启动时创建 Collection |
| `@Nullable` | 标记可为 null 的依赖 | 所有外部服务依赖 |
| `@ConditionalOnExpression` | 条件创建 Bean | DashScopeConfig 中无 API Key 时不创建 |

### 2.4 面试要点

-  Spring Boot 自动配置原理：`@EnableAutoConfiguration` → `spring.factories` → `AutoConfigurationImportSelector` → 条件注解过滤
- Bean 的生命周期：实例化 → 属性赋值 → 初始化（@PostConstruct）→ 使用 → 销毁（@PreDestroy）
- Bean 作用域：singleton（默认）、prototype、request、session

## 3. Maven 多模块构建

### 3.1 核心概念

Maven 是 Java 生态的**项目管理和构建工具**，核心功能：

- **依赖管理**：声明式管理第三方库，自动传递依赖
- **生命周期**：clean → compile → test → package → install → deploy
- **多模块构建**：一个父 POM 管理多个子模块，统一版本和构建配置

### 3.2 EduMate 的多模块结构

```
EduMate/
├── pom.xml                    # 父 POM（版本管理、公共依赖）
├── edumate-common/            # 通用模块（数据模型、枚举）
├── edumate-core/              # 核心业务模块（Service 层）
└── edumate-admin/             # 启动模块（Controller + Config）
```

**模块依赖关系**：

```
edumate-admin → edumate-core → edumate-common
```

- `edumate-common`：被所有模块依赖，定义共享的 Model 和 Enum
- `edumate-core`：依赖 common，实现核心业务逻辑
- `edumate-admin`：依赖 core，作为启动入口

### 3.3 父 POM 的作用

在父 POM 的 `<dependencyManagement>` 中统一声明版本号，子模块引用时无需指定版本：

```xml
<!-- 父 POM -->
<dependencyManagement>
    <dependencies>
        <dependency>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-dependencies</artifactId>
            <version>3.4.5</version>
            <type>pom</type>
            <scope>import</scope>
        </dependency>
    </dependencies>
</dependencyManagement>
```

### 3.4 Maven Wrapper

项目使用 `mvnw.cmd`（Maven Wrapper），无需全局安装 Maven，自动下载指定版本：

```bash
mvnw.cmd clean install -DskipTests
```

### 3.5 面试要点

- Maven 的生命周期阶段：validate → compile → test → package → verify → install → deploy
- 依赖传递与冲突解决：最短路径优先、先声明优先
- `<dependencyManagement>` vs `<dependencies>`：前者声明版本不实际引入，后者实际引入依赖
- Maven Wrapper 的优势：统一构建环境，避免"在我机器上能跑"的问题

## 4. LangChain4j 框架

### 4.1 核心概念

LangChain4j 是 Java 生态的 LLM 应用开发框架，对标 Python 的 LangChain。它提供了统一的抽象层，屏蔽不同 LLM 提供商的 API 差异。

### 4.2 核心抽象

| 抽象 | 作用 | EduMate 使用 |
|------|------|-------------|
| **ChatModel** | 对话模型（生成文本） | 问答生成、知识抽取、意图识别、出题 |
| **EmbeddingModel** | 嵌入模型（文本→向量） | 文档向量化、Query 向量化 |
| **EmbeddingStore** | 向量存储抽象 | 通过 Qdrant 实现 |
| **ChatMessage** | 消息抽象（UserMessage / AiMessage / SystemMessage） | 构建 Prompt |
| **ChatResponse** | 对话响应（含 AiMessage + TokenUsage） | 获取 LLM 回复 |

### 4.3 EduMate 中的使用

```java
// 发送消息给 LLM
ChatResponse response = chatModel.chat(UserMessage.from("什么是红黑树？"));
String answer = response.aiMessage().text();

// 批量向量化
List<TextSegment> segments = chunks.stream()
    .map(c -> TextSegment.from(c.getContent(), metadata))
    .toList();
embeddingModel.embedAll(segments);

// 检索
List<EmbeddingMatch<TextSegment>> results = embeddingStore.search(
    Embedding.from(embeddingModel.embed(query).content()), topK, 0.7);
```

### 4.4 版本注意事项

- EduMate 使用 LangChain4j **1.17.2-beta27**（Qdrant 集成使用 beta 版本）
- `ChatModel` 类位于 `dev.langchain4j.model.chat.ChatModel`
- `AiMessage` 类位于 `dev.langchain4j.data.message.AiMessage`（非 `dev.langchain4j.model.chat.response`）
- ChatModel 的 `chat()` 方法存在重载，使用 `UserMessage.from()` 避免歧义

### 4.5 面试要点

- LangChain4j vs LangChain（Python）：前者是 Java 原生实现，类型安全、适合企业级 Spring Boot 集成
- LangChain4j 的模块化设计：core（核心抽象）+ 社区适配器（各 LLM 提供商）
- ChatModel vs ChatLanguageModel：LangChain4j 1.17+ 统一为 ChatModel

## 5. 文档解析与处理（PDFBox / POI）

### 5.1 核心概念

文档解析是将用户上传的课程资料（PDF、PPTX、DOCX、TXT、MD）转换为可处理的纯文本。

### 5.2 使用的库

| 库 | 版本 | 支持格式 | 特点 |
|----|------|---------|------|
| **Apache PDFBox** | 3.0.4 | PDF | 纯 Java 实现，可提取文本、图片、元数据 |
| **Apache POI** | 5.4.0 | PPTX / DOCX | 支持 Office 2007+ 格式 |
| 原生 Java | - | TXT / MD | 直接读取字符流 |

### 5.3 EduMate 实现

`DocumentParserService` 根据文件扩展名选择解析器：

```java
public List<DocumentChunk> parse(MultipartFile file, String courseName) {
    String extension = getExtension(file.getOriginalFilename());
    String text = switch (extension) {
        case "pdf" -> parsePdf(file);    // PDFBox 逐页提取
        case "pptx" -> parsePptx(file);  // POI 逐幻灯片提取
        case "docx" -> parseDocx(file);  // POI 逐段落提取
        default -> parseText(file);      // 直接读取
    };
    return hierarchicalChunkerService.chunk(text, courseName);
}
```

### 5.4 面试要点

- PDFBox vs iText：PDFBox 是 Apache 开源（Apache 2.0），iText 有 AGPL 许可限制
- POI 处理大文件：使用 `SXSSFWorkbook`（流式）代替 `XSSFWorkbook`（内存）
- 为什么需要文档解析：LLM 无法直接理解二进制格式，需要转换为纯文本供后续处理

## 6. 层级感知文档切分

### 6.1 核心概念

文档切分（Chunking）是将长文档拆分为适合检索的短片段。**层级感知切分**在切分时保留文档的结构信息（章→节→小节），使检索结果具有上下文。

### 6.2 为什么需要层级切分

| 普通切分 | 层级感知切分 |
|---------|-------------|
| 每个块独立，丢失结构信息 | 每个块记录所属章节（chapterPath） |
| 检索结果不包含上下文 | 检索结果可展开父块（parentChunkId） |
| 如："B+树是…" | 如："第3章 > 3.2节 > B+树：B+树是…" |

### 6.3 EduMate 实现

`HierarchicalChunkerService` 的核心参数：

```
最大块大小：2000 字符
重叠大小：  200 字符（滑动窗口，保证上下文连续性）
```

切分策略：

1. **逐行扫描**：用正则匹配章节标题（`第X章`、`X.Y` 编号）
2. **按层级累积**：同一章节的内容累积到当前块
3. **超限切分**：块超过 2000 字符时强制切分
4. **重叠保留**：新块开头保留前一块最后 200 字符，防止语义断裂

```java
// 正则匹配
private static final Pattern CHAPTER_PATTERN = Pattern.compile("^第[一二三四五六七八九十\\d]+章");
private static final Pattern SECTION_PATTERN = Pattern.compile("^\\d+\\.\\d+");

// 超限切分，保留重叠
if (currentChunk.length() > MAX_CHUNK_SIZE) {
    flushChunk(chunks, currentChunk.substring(0, MAX_CHUNK_SIZE), ...);
    String overlap = currentChunk.substring(currentChunk.length() - OVERLAP_SIZE);
    currentChunk = new StringBuilder(overlap);
}
```

### 6.4 面试要点

- 为什么需要重叠（Overlap）：防止关键信息恰好落在切分边界上被截断
- 固定大小切分 vs 语义切分：前者简单但可能切断语义，后者（如按段落、按句子）更智能
- 块大小如何选择：取决于 Embedding 模型的上下文窗口和检索精度需求，通常 500-2000 字符

## 7. 向量嵌入与相似度计算

### 7.1 核心概念

**Embedding（向量嵌入）**是将文本映射到高维向量空间的过程。语义相近的文本在向量空间中距离更近。

```
"红黑树是一种自平衡二叉查找树" → [0.034, -0.127, 0.456, ..., 0.089]  (1024维)
```

### 7.2 使用的模型

EduMate 使用阿里云通义千问的 **text-embedding-v3** 模型：

- 输出维度：**1024 维**
- 支持中英文
- 通过 DashScope API 调用

### 7.3 相似度计算

EduMate 使用 **Cosine 相似度**（余弦相似度）：

```
Cosine(A, B) = (A · B) / (|A| × |B|)
```

- 值域：[-1, 1]，越接近 1 表示越相似
- 优点：不受向量长度影响，只关注方向
- 对比：欧氏距离（受绝对距离影响）、点积（受向量模长影响）

### 7.4 面试要点

- 为什么用 Cosine 而非欧氏距离：Cosine 归一化后对高频词和低频词公平，不受文本长度影响
- Embedding 模型的选型：维度（越高越精确但成本越高）、支持语言、最大输入长度
- 向量数据库 vs 传统数据库：向量数据库针对高维向量的近似最近邻搜索（ANN）进行了优化，支持 HNSW、IVF 等索引算法

## 8. Qdrant 向量数据库

### 8.1 核心概念

Qdrant 是一个高性能的**向量相似度搜索引擎**，专门用于存储和检索高维向量。

### 8.2 核心特性

| 特性 | 说明 |
|------|------|
| **通信协议** | gRPC（端口 6334）+ REST API（端口 6333） |
| **索引算法** | HNSW（Hierarchical Navigable Small World） |
| **距离度量** | Cosine、Euclidean、Dot Product |
| **过滤** | 支持基于 Payload 的标量过滤（如 courseName、chapterPath） |
| **Collection** | 类似关系数据库的"表"，每个 Collection 有固定的向量维度 |

### 8.3 EduMate 实现

`QdrantConfig` 在应用启动时自动创建 Collection：

```java
@PostConstruct
public void init() {
    // 检查 Collection 是否存在
    boolean exists = qdrantClient.collectionExistsAsync("edumate-docs").get();
    if (!exists) {
        // 创建 Collection：1024 维，Cosine 距离
        qdrantClient.createCollectionAsync("edumate-docs",
            VectorParams.newBuilder()
                .setSize(1024)
                .setDistance(Distance.Cosine)
                .build()).get();
    }
}
```

`VectorStoreService` 的检索流程：

```java
// 1. 将查询文本向量化
Embedding queryEmbedding = embeddingModel.embed(query).content();

// 2. 在 Qdrant 中搜索 Top-K 相似向量
List<EmbeddingMatch<TextSegment>> results = embeddingStore.search(
    Embedding.from(queryEmbedding), topK, 0.7  // 0.7 是最小相似度阈值
);

// 3. 转换回 DocumentChunk
return results.stream()
    .map(match -> DocumentChunk.builder()
        .content(match.embedded().text())
        .score(match.score())
        .build())
    .toList();
```

### 8.4 面试要点

- Qdrant vs Milvus vs Weaviate：Qdrant 用 Rust 编写，性能高、部署简单（单二进制文件），适合中小规模
- HNSW 算法原理：多层图结构，上层稀疏（快速定位区域），下层密集（精确搜索），以空间换时间
- 为什么用 gRPC 而非 REST：gRPC 基于 HTTP/2，二进制传输，性能更高；但调试不如 REST 方便

## 9. Elasticsearch 与 BM25 关键词检索

### 9.1 核心概念

Elasticsearch 是一个基于 Lucene 的**分布式搜索和分析引擎**。在 EduMate 中，它作为关键词检索引擎，补充向量检索的不足。

### 9.2 BM25 算法

BM25（Best Matching 25）是 Elasticsearch 默认的相关性评分算法，基于 TF-IDF 的改进：

```
BM25(q, d) = Σ IDF(qi) × (TF(qi, d) × (k1 + 1)) / (TF(qi, d) + k1 × (1 - b + b × |d|/avgdl))
```

- **TF（词频）**：词在文档中出现的次数
- **IDF（逆文档频率）**：词的稀有程度（越稀有越重要）
- **k1、b**：调节参数，控制词频饱和度和文档长度归一化

### 9.3 向量检索 vs 关键词检索

| 维度 | 向量检索（Qdrant） | 关键词检索（ES BM25） |
|------|-------------------|---------------------|
| **匹配方式** | 语义相似度 | 精确关键词匹配 |
| **优势** | 理解同义词、近义词、语义相似 | 精确匹配专业术语、缩写、代码 |
| **劣势** | 对罕见专业术语可能召回不准 | 无法理解语义变化 |
| **示例** | "自平衡二叉树" → 能匹配"红黑树" | "B+树" → 精确匹配"B+树" |

### 9.4 EduMate 实现

`ElasticsearchConfig` 使用官方 `elasticsearch-java` 客户端：

```java
@Bean
public ElasticsearchClient elasticsearchClient() {
    RestClient restClient = RestClient.builder(
        new HttpHost("localhost", 9200, "http")).build();
    ElasticsearchTransport transport = new RestClientTransport(
        restClient, new JacksonJsonpMapper());
    return new ElasticsearchClient(transport);
}
```

### 9.5 面试要点

- BM25 vs TF-IDF：BM25 引入了文档长度归一化和词频饱和度控制，效果更好
- Elasticsearch 的倒排索引原理：词 → 文档列表的映射，查询时直接定位
- 为什么需要关键词检索：向量检索对精确术语（如"B+树"、"TCP三次握手"）的召回可能不如关键词匹配

## 10. Neo4j 与知识图谱

### 10.1 核心概念

**知识图谱（Knowledge Graph）**是以图结构（节点 + 边）组织知识的方式，能表达实体之间的复杂关系。

**Neo4j** 是最流行的图数据库，使用属性图模型（Property Graph Model）：

- **节点（Node）**：实体，有标签（Label）和属性（Property）
- **关系（Relationship）**：节点间的连接，有类型（Type）和属性
- **路径（Path）**：节点和关系组成的序列

### 10.2 EduMate 中的知识图谱

```
(数据结构) -[:PREREQUISITE]-> (数组)
(数组) -[:SUCCESSOR]-> (链表)
(链表) -[:PREREQUISITE]-> (二叉树)
(二叉树) -[:SUCCESSOR]-> (红黑树)
(红黑树) -[:APPLIED_IN]-> (B+树索引)
(B+树) -[:BELONGS_TO]-> (数据库原理)
```

### 10.3 关系类型

| 关系类型 | 含义 | 示例 |
|---------|------|------|
| **PREREQUISITE** | 前置知识 | 数组 → 链表 |
| **SUCCESSOR** | 后继知识 | 链表 → 二叉树 |
| **RELATED_TO** | 关联 | 红黑树 ↔ AVL 树 |
| **BELONGS_TO** | 属于 | B+树 → 数据库原理 |
| **APPLIED_IN** | 应用 | 红黑树 → HashMap |

### 10.4 EduMate 实现

使用**原生 Neo4j Java Driver**（非 Spring Data Neo4j），直接执行 Cypher 查询：

```java
// 知识图谱存储：MERGE 实现 upsert
try (var session = driver.session()) {
    session.executeWrite(tx -> {
        for (KnowledgePoint point : points) {
            // MERGE 节点（存在则复用，不存在则创建）
            tx.run("MERGE (k:KnowledgePoint {name: $name}) " +
                   "SET k.description = $desc, k.courseName = $course, " +
                   "k.chapterPath = $chapter, k.sourceChunkId = $chunkId",
                   parameters);
            // MERGE 关系
            for (KnowledgeRelation rel : point.getRelations()) {
                tx.run("MERGE (target:KnowledgePoint {name: $targetName})",
                       Map.of("targetName", rel.getTargetName()));
                tx.run("MATCH (a:KnowledgePoint {name: $name}), " +
                       "(b:KnowledgePoint {name: $targetName}) " +
                       "MERGE (a)-[r:" + rel.getType() + "]->(b)",
                       parameters);
            }
        }
        return null;
    });
}
```

### 10.5 图谱检索

`GraphSearchService` 支持多跳遍历：

```cypher
-- 双向 1 跳遍历，查找知识点及其关联
MATCH (k:KnowledgePoint) WHERE k.name CONTAINS $query
OPTIONAL MATCH (k)-[r]->(related:KnowledgePoint)
WHERE type(r) IN ['PREREQUISITE', 'SUCCESSOR', 'RELATED_TO', 'APPLIED_IN']
RETURN k, r, related
UNION
MATCH (related:KnowledgePoint)-[r]->(k:KnowledgePoint)
WHERE k.name CONTAINS $query
RETURN k, r, related
```

### 10.6 面试要点

- 图数据库 vs 关系数据库：图数据库用原生图存储和遍历，多跳查询性能远优于 SQL 的 JOIN
- Neo4j 的索引：自动为设置了约束的属性创建索引，支持全文索引
- 知识图谱的构建方式：规则抽取（正则/模板）→ 机器学习（NER + 关系抽取）→ LLM（Few-shot 抽取）
- 为什么需要知识图谱：提供结构化的知识关联，支持多跳推理（如"学红黑树之前需要掌握什么？"）

## 11. 混合检索与 RRF 融合排序

### 11.1 核心概念

**混合检索（Hybrid Search）**是同时使用多种检索策略（向量检索 + 关键词检索 + 图谱检索），然后将结果融合排序的方法。

### 11.2 为什么需要混合检索

单一检索方式各有盲区：

```
向量检索：           关键词检索：          图谱检索：
擅长语义匹配         擅长精确术语匹配       擅长关系推理
"自平衡二叉树"        "B+树"               "红黑树的前置知识"
→ 能匹配"红黑树"      → 精确命中"B+树"      → 能找出"二叉查找树"
✗ 对"TCP"不敏感       ✗ 对"二叉查找树"不敏感  ✗ 对未入库知识点无效
```

### 11.3 RRF（Reciprocal Rank Fusion）

RRF 是一种**免训练的融合算法**，通过排名倒数加权合并多路结果：

```
RRF_score(d) = Σ 1 / (k + rank_i(d))

其中：
- k = 60（经典常数，平滑排名差异）
- rank_i(d) = 文档 d 在第 i 路检索中的排名（从 1 开始）
```

**核心思想**：在多个路径中都排名靠前的文档，更可能是相关文档。

**示例**：

| 文档 | 向量排名 | 关键词排名 | 图谱排名 | RRF 分数 |
|------|---------|-----------|---------|---------|
| B+树详解 | 1 | 3 | 2 | 1/(60+1) + 1/(60+3) + 1/(60+2) = 0.048 |
| 数据库索引 | 2 | 1 | - | 1/(60+2) + 1/(60+1) = 0.032 |
| 文件系统 | 3 | - | - | 1/(60+3) = 0.016 |

### 11.4 EduMate 实现

`HybridSearchService` 三路并行检索：

```java
public List<DocumentChunk> search(String query, int topK) {
    // 每路多取，为融合留空间
    int retrievalTopK = topK * 2;

    // 并行执行三路检索（每路内部有降级处理）
    List<DocumentChunk> vectorResults = vectorStoreService.search(query, retrievalTopK);
    List<DocumentChunk> keywordResults = keywordIndexService.search(query, retrievalTopK);
    List<DocumentChunk> graphResults = graphSearchService.search(query, retrievalTopK);

    // RRF 三路融合
    return rrfusionService.fuse(vectorResults, keywordResults, graphResults, topK);
}
```

`RRFusionService` 融合算法：

```java
private static final double K = 60.0;

public List<DocumentChunk> fuse(List<DocumentChunk>... resultLists) {
    Map<String, DocumentChunk> chunkMap = new LinkedHashMap<>();
    Map<String, Double> scores = new HashMap<>();

    for (List<DocumentChunk> results : resultLists) {
        for (int i = 0; i < results.size(); i++) {
            DocumentChunk chunk = results.get(i);
            String id = chunk.getId();
            chunkMap.putIfAbsent(id, chunk);
            double score = 1.0 / (K + i + 1);  // rank 从 1 开始
            scores.merge(id, score, Double::sum);
        }
    }

    // 按 RRF 得分降序排列，取 Top-K
    return scores.entrySet().stream()
        .sorted(Map.Entry.<String, Double>comparingByValue().reversed())
        .limit(topK)
        .map(e -> chunkMap.get(e.getKey()).withScore(e.getValue()))
        .toList();
}
```

### 11.5 面试要点

- RRF 为什么 k=60：经验值，k 越大排名差异被平滑得越厉害；k 太小则第一名的权重过高
- RRF vs 加权求和：RRF 不需要归一化不同检索器的分数（不同检索器的分数分布不同），更鲁棒
- 为什么先多取再融合：每路多取（topK*2）为融合留空间，避免某路的好结果因取的太少而被遗漏

## 12. Redis 会话管理

### 12.1 核心概念

Redis 是高性能的**内存键值数据库**，在 EduMate 中用于存储多轮对话的会话历史。

### 12.2 为什么用 Redis

| 方案 | 优点 | 缺点 |
|------|------|------|
| **内存 Map** | 最简单 | 应用重启丢失、不支持分布式 |
| **数据库** | 持久化 | 读写慢、不适合高频会话操作 |
| **Redis** | 高性能、支持 TTL、分布式友好 | 需要额外部署 |

### 12.3 EduMate 实现

`ChatSessionService` 使用 Redis List 存储会话：

```java
// Key 格式
private static final String KEY_PREFIX = "chat:session:";

// 添加消息
public void addMessage(String sessionId, ChatMessage message) {
    String key = KEY_PREFIX + sessionId;
    String json = objectMapper.writeValueAsString(message);
    redisTemplate.opsForList().rightPush(key, json);  // 追加到列表末尾
    redisTemplate.opsForList().trim(key, -20, -1);     // 保留最近 20 条
    redisTemplate.expire(key, Duration.ofMinutes(30));  // TTL 30 分钟
}

// 获取历史
public List<ChatMessage> getHistory(String sessionId) {
    String key = KEY_PREFIX + sessionId;
    List<String> jsonList = redisTemplate.opsForList().range(key, 0, -1);
    return jsonList.stream()
        .map(json -> objectMapper.readValue(json, ChatMessage.class))
        .toList();
}
```

### 12.4 面试要点

- Redis 数据结构：String、List、Set、Sorted Set、Hash、Stream
- Redis 过期策略：惰性删除 + 定期删除
- Redis 持久化：RDB（快照）vs AOF（追加日志）
- 为什么用 List 而非 String：List 天然支持追加和裁剪，适合消息队列场景

## 13. SSE 流式响应

### 13.1 核心概念

**SSE（Server-Sent Events）**是一种服务器向客户端推送数据的 HTTP 协议，基于标准 HTTP 连接，单向传输（服务器 → 客户端）。

### 13.2 SSE vs WebSocket vs 轮询

| 方案 | 连接 | 方向 | 协议 | 适用场景 |
|------|------|------|------|---------|
| **轮询** | 短连接 | 客户端→服务器 | HTTP | 简单但浪费资源 |
| **SSE** | 长连接 | 服务器→客户端 | HTTP | 单向推送（如 AI 流式输出） |
| **WebSocket** | 长连接 | 双向 | WS | 实时双向通信（如聊天） |

### 13.3 EduMate 实现

`ChatController` 使用 Spring MVC 的 `SseEmitter`：

```java
@PostMapping(value = "/stream", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
public SseEmitter streamChat(@RequestBody StreamRequest request) {
    SseEmitter emitter = new SseEmitter(300_000L); // 5 分钟超时

    executor.execute(() -> {
        try {
            // 1. 拒答检查
            // 2. 构建上下文
            // 3. LLM 生成
            String fullAnswer = chatModel.chat(UserMessage.from(context))
                .aiMessage().text();

            // 4. 模拟逐 token 推送
            for (int i = 0; i < fullAnswer.length(); i += 5) {
                String chunk = fullAnswer.substring(i, Math.min(i + 5, fullAnswer.length()));
                emitter.send(SseEmitter.event()
                    .name("message")
                    .data(chunk));
                Thread.sleep(20); // 模拟流式延迟
            }

            // 5. 发送完成信号
            emitter.send(SseEmitter.event().name("done")
                .data(Map.of("status", "DONE", "sessionId", sessionId)));
            emitter.complete();
        } catch (Exception e) {
            emitter.completeWithError(e);
        }
    });

    return emitter;
}
```

### 13.4 面试要点

- SSE 的数据格式：`data: xxx\n\n`（纯文本）或 `event: xxx\ndata: xxx\n\n`（带事件类型）
- SSE 的自动重连：浏览器原生支持，断线后自动重连
- SSE 的局限性：单向通信（服务器→客户端），不支持二进制数据
- 为什么用 SSE 而非 WebSocket：AI 流式输出是典型的单向推送场景，SSE 更轻量，无需升级协议

## 14. Agent 智能体与 ReAct 模式

### 14.1 核心概念

**Agent（智能体）**是能自主规划、使用工具、执行多步任务的 AI 系统。与简单的"一问一答"不同，Agent 能：

- **规划（Plan）**：拆解复杂任务为子步骤
- **执行（Execute）**：调用工具（检索、计算、API）
- **观察（Observe）**：评估执行结果
- **迭代（Iterate）**：根据结果调整策略

### 14.2 ReAct 模式

**ReAct（Reasoning + Acting）**是一种将推理和行动交替进行的 Agent 模式：

```
思考 → 行动 → 观察 → 思考 → 行动 → 观察 → ... → 最终答案
```

### 14.3 EduMate 实现

`QuizAgentService` 使用简化的 ReAct 模式出题：

```
Step 1 - Plan（规划）：
  内置 Prompt 指导 LLM：
  - 确定出题范围（课程名称、知识点）
  - 确定题型分布（选择题 40%、判断题 20%、简答题 40%）

Step 2 - Execute（执行）：
  调用 LLM 生成 JSON 格式题目：
  {
    "stem": "以下哪种数据结构是自平衡的？",
    "type": "CHOICE",
    "options": ["A. 普通二叉搜索树", "B. 红黑树", ...],
    "answer": "B",
    "explanation": "红黑树通过颜色标记和旋转操作保持平衡..."
  }

Step 3 - Verify（验证）：
  过滤不合格题目：
  - 题干为空 → 丢弃
  - 答案为空 → 丢弃
  - 题目数量不足 → 降级重试
```

### 14.4 面试要点

- ReAct vs Chain-of-Thought（CoT）：CoT 只有推理没有行动，ReAct 交替进行推理和行动
- Agent 的核心组件：LLM（大脑）、Tools（工具）、Memory（记忆）、Planning（规划）
- Agent 的挑战：幻觉（行动不可靠）、无限循环、工具调用失败

## 15. 意图识别

### 15.1 核心概念

意图识别是判断用户输入属于哪种类型的任务，以便系统选择合适的处理流程。

### 15.2 EduMate 的意图分类

`IntentClassifierService` 将用户输入分为四类：

| 意图类型 | 说明 | 示例 | 处理方式 |
|---------|------|------|---------|
| **COURSE_QA** | 课程问答 | "红黑树有哪些性质？" | 标准 RAG 问答流程 |
| **QUIZ_GENERATION** | 出题请求 | "帮我出几道数据结构的题" | 路由到 QuizAgent |
| **CONCEPT_EXPLANATION** | 概念解释 | "什么是三次握手？" | 提取知识点，检索相关内容 |
| **REFUSAL** | 拒绝回答 | "帮我写作业" | 触发拒答守卫 |

### 15.3 实现方式

使用 LLM + Few-shot Prompt 进行分类：

```java
String prompt = """
    你是一个意图分类器。请将用户输入分为以下类别之一：
    - COURSE_QA: 课程内容问答
    - QUIZ_GENERATION: 出题请求
    - CONCEPT_EXPLANATION: 概念解释
    - REFUSAL: 超出课程范围或违规请求

    示例：
    "红黑树的特点" → COURSE_QA
    "帮我出5道题" → QUIZ_GENERATION
    "什么是B+树" → CONCEPT_EXPLANATION

    用户输入: %s
    分类结果:""";
```

### 15.4 面试要点

- 意图识别的实现方式：规则匹配（简单快速）→ 机器学习分类器（需训练数据）→ LLM 分类（灵活但成本高）
- 多意图处理：一个用户输入可能包含多个意图，需要优先级排序或并行处理
- 意图识别的降级：LLM 不可用时使用规则匹配或默认意图

## 16. Query 改写

### 16.1 核心概念

用户输入的查询通常是口语化的、简短的，不适合直接用于检索。Query 改写将用户原始查询转换为更适合检索引擎的格式。

### 16.2 改写策略

| 原始查询 | 改写后 | 改写策略 |
|---------|--------|---------|
| "红黑树" | "红黑树 定义 结构 特点 旋转操作 应用场景" | 扩展关键术语 |
| "B+树和B树有啥区别" | "B+树 B树 区别 对比 数据结构 索引" | 口语转书面 + 补充关联概念 |
| "那个平衡二叉树怎么转" | "平衡二叉树 旋转操作 AVL树 LL RR LR RL" | 消歧 + 补充专业术语 |

### 16.3 EduMate 实现

`QueryRewriteService` 使用 LLM 进行改写：

```java
private static final String REWRITE_PROMPT = """
    你是一个查询优化器。将用户简短查询扩展为更利于检索的语句。
    规则：
    1. 保留原意，不添加额外内容
    2. 扩展关键术语和同义词
    3. 补充关联概念
    4. 去除口语化表达

    原始查询: %s
    优化后:""";

public String rewrite(String query) {
    if (chatModel == null) return query;  // 降级：返回原始查询
    ChatResponse response = chatModel.chat(UserMessage.from(
        String.format(REWRITE_PROMPT, query)));
    return response.aiMessage().text();
}
```

### 16.4 面试要点

- Query 改写 vs Query 扩展：改写是替换，扩展是追加
- 改写可能引入噪音：过度扩展可能引入不相关术语，需要平衡
- 改写的历史感知：多轮对话中，改写应结合历史上下文（如"它的性质呢？"→"红黑树的性质"）

## 17. 拒答守卫

### 17.1 核心概念

拒答守卫（Refusal Guard）是 AI 系统的安全边界，防止系统回答超出范围或违规的问题。

### 17.2 EduMate 的两层过滤

`RefusalGuardService` 实现两层过滤：

**第一层：关键词规则（快速过滤）**

```java
private static final List<Pattern> BLOCKED_PATTERNS = List.of(
    Pattern.compile("代写|代做|帮.*写.*作业|帮.*做.*作业"),
    Pattern.compile("考试.*答案|期末.*答案|试卷.*答案"),
    Pattern.compile("作弊|抄袭|替考"),
    Pattern.compile("与课程无关|与学习无关")
);
```

**第二层：LLM 判断（二次确认）**

当关键词规则无法覆盖时，用 LLM 判断问题是否超出课程范围：

```java
public RefusalResult shouldRefuse(String query) {
    // 第一层：关键词匹配
    for (Pattern pattern : BLOCKED_PATTERNS) {
        if (pattern.matcher(query).find()) {
            return new RefusalResult(true,
                "抱歉，我不能回答与学术诚信相关的问题。");
        }
    }

    // 第二层：LLM 判断（可选，关键词已覆盖大部分场景）
    if (chatModel != null) {
        String prompt = "判断以下问题是否适合由课程学习助手回答...";
        ChatResponse response = chatModel.chat(UserMessage.from(prompt));
        if (parseRefusal(response.aiMessage().text())) {
            return new RefusalResult(true,
                "抱歉，这个问题超出了课程学习范围。");
        }
    }

    return new RefusalResult(false, null);
}
```

### 17.3 面试要点

- 为什么需要两层过滤：规则层快速、低成本、100% 可控；LLM 层灵活、能处理复杂语义
- 拒答的边界设计：过严（影响用户体验）vs 过松（安全风险）
- 其他拒答策略：基于 Embedding 的语义相似度（判断问题是否在知识库范围内）

## 18. RAGAS 评测框架

### 18.1 核心概念

RAGAS（Retrieval Augmented Generation Assessment）是专门用于评估 RAG 系统的开源框架。它使用 **LLM-as-Judge** 模式，让 LLM 评判 RAG 系统的输出质量。

### 18.2 三个核心指标

| 指标 | 评估对象 | 评估方式 | 满分含义 |
|------|---------|---------|---------|
| **Answer Relevance** | 生成的答案 | 从答案中生成反向问题，判断与原问题的相似度 | 答案与问题高度相关 |
| **Faithfulness** | 生成的答案 | 从答案中提取陈述，判断每个陈述是否被上下文支持 | 答案完全基于上下文，无幻觉 |
| **Context Relevance** | 检索的上下文 | 判断上下文中有多少句子与问题相关 | 检索到的上下文与问题高度相关 |

### 18.3 EduMate 实现

`RagasEvaluationService` 为每个指标设计专用 Prompt：

```java
// Answer Relevance
String prompt = """
    你是一个评估专家。请评估以下答案与问题的相关性。
    只输出 0-100 的分数，不要输出其他文字。

    问题: %s
    答案: %s
    相关度得分:""";

// Faithfulness
String prompt = """
    你是一个评估专家。请评估以下答案是否忠实于提供的上下文。
    只输出 0-100 的分数，不要输出其他文字。

    上下文: %s
    答案: %s
    忠实度得分:""";
```

### 18.4 面试要点

- 为什么用 LLM-as-Judge 而非人工评估：成本低、可自动化、可扩展
- LLM-as-Judge 的局限性：LLM 自身可能有偏见、对长文本评估不准确、分数离散度大
- RAGAS 的其他指标：Answer Correctness、Aspect Critique、Context Recall

## 19. 检索评测指标

### 19.1 Recall@K

**召回率**：前 K 个结果中相关文档占所有相关文档的比例。

```
Recall@K = |检索到的相关文档 ∩ 前K个结果| / |所有相关文档|
```

**示例**：相关文档共 5 篇，前 3 个结果中有 2 篇相关 → Recall@3 = 2/5 = 0.4

**EduMate 支持**：Recall@1、Recall@3、Recall@5、Recall@10

### 19.2 MRR（Mean Reciprocal Rank）

**平均倒数排名**：第一个相关文档出现位置的倒数的平均值。

```
MRR = (1/N) × Σ 1/rank_i

其中 rank_i 是第 i 个查询中第一个相关文档的排名
```

**示例**：查询 1 第一个相关文档排第 2 → 1/2；查询 2 排第 1 → 1/1；查询 3 排第 4 → 1/4
MRR = (0.5 + 1.0 + 0.25) / 3 = 0.583

### 19.3 NDCG@K

**归一化折损累计增益**：考虑排名位置和相关性等级的排序质量指标。

```
DCG@K = Σ (2^rel_i - 1) / log₂(i+1)
NDCG@K = DCG@K / IDCG@K（理想排序下的 DCG）
```

- 排名越靠前，折扣因子越大（log₂(i+1)）
- 相关性越高，收益越大（2^rel_i - 1，指数增长）

### 19.4 EduMate 实现

`EvaluationMetricsService` 是纯函数实现，可独立测试：

```java
public double recallAtK(List<String> retrieved, Set<String> relevant, int k) {
    long hits = retrieved.stream().limit(k).filter(relevant::contains).count();
    return relevant.isEmpty() ? 0.0 : (double) hits / relevant.size();
}

public double mrr(List<List<String>> allRetrieved, List<Set<String>> allRelevant) {
    double sum = 0;
    for (int i = 0; i < allRetrieved.size(); i++) {
        for (int j = 0; j < allRetrieved.get(i).size(); j++) {
            if (allRelevant.get(i).contains(allRetrieved.get(i).get(j))) {
                sum += 1.0 / (j + 1);
                break;
            }
        }
    }
    return sum / allRetrieved.size();
}
```

### 19.5 面试要点

- Recall vs Precision：Recall 关注"找全了没"，Precision 关注"找对了没"
- 为什么用 MRR 而非准确率：MRR 关注第一个正确答案的排名，更符合用户行为（通常只看前几个结果）
- NDCG 的优势：支持多级相关性（非常相关、部分相关、不相关），更精细

## 20. 全链路 Trace 追踪

### 20.1 核心概念

全链路 Trace 记录一次请求在系统中经过的所有阶段的**输入、输出、耗时和状态**，用于性能分析和问题排查。

### 20.2 EduMate 的追踪阶段

`TraceService` 追踪 8 个阶段：

```
queryRewrite → intentClassification → refusalCheck
  → vectorRetrieval → keywordRetrieval → graphRetrieval
  → rrfFusion → llmGeneration
```

### 20.3 实现

```java
// 内存存储
private final ConcurrentHashMap<String, TraceRecord> traces = new ConcurrentHashMap<>();
private final ConcurrentLinkedDeque<String> traceIds = new ConcurrentLinkedDeque<>();
private static final int MAX_TRACES = 200;

// 记录追踪
public TraceRecord startTrace(String query, String sessionId) {
    String traceId = UUID.randomUUID().toString().substring(0, 8);
    TraceRecord record = TraceRecord.builder()
        .traceId(traceId).query(query).sessionId(sessionId)
        .timestamp(Instant.now()).build();
    traces.put(traceId, record);
    traceIds.addLast(traceId);

    // FIFO 淘汰
    while (traceIds.size() > MAX_TRACES) {
        String oldest = traceIds.pollFirst();
        traces.remove(oldest);
    }
    return record;
}

// 记录阶段完成
public void recordStage(String traceId, String stage,
                        Object input, Object output,
                        long durationMs, boolean success) {
    TraceRecord record = traces.get(traceId);
    if (record != null) {
        record.getStages().add(TraceRecord.StageRecord.builder()
            .stage(stage).inputSummary(truncate(input))
            .outputSummary(truncate(output))
            .durationMs(durationMs).success(success).build());
    }
}
```

### 20.4 面试要点

- Trace vs Log vs Metric：Trace 关注请求链路，Log 关注离散事件，Metric 关注聚合指标
- 分布式追踪标准：OpenTelemetry、Jaeger、Zipkin
- 为什么用内存存储：简单、无外部依赖；生产环境应替换为持久化存储

## 22. 降级设计模式

### 22.1 核心概念

降级（Degradation）是当系统部分功能不可用时，自动切换到备用方案，保证核心功能正常运行的设计模式。

### 22.2 EduMate 的降级策略

| 服务不可用 | 降级行为 | 影响范围 |
|-----------|----------|---------|
| **ChatModel（LLM）** | 知识抽取返回空、出题返回空、意图识别返回默认值、Query 改写返回原文 | 知识图谱、出题、智能功能不可用，基础检索仍可用 |
| **EmbeddingModel** | 向量索引和检索跳过 | 向量检索不可用，关键词检索仍可用 |
| **Elasticsearch Client** | 关键词检索返回空列表 | 混合检索退化为向量检索 |
| **Neo4j Driver** | 图谱存储和检索跳过 | 混合检索退化为向量+关键词 |
| **Redis** | 会话历史返回空列表 | 多轮对话退化为单轮问答 |

### 22.3 实现方式

使用 `@Nullable` 注入 + 条件判断：

```java
public KnowledgeExtractionService(@Nullable ChatModel chatModel) {
    this.chatModel = chatModel;
}

public List<KnowledgePoint> extract(List<DocumentChunk> chunks) {
    if (chatModel == null) {
        log.warn("ChatModel 不可用，跳过知识抽取");
        return List.of();
    }
    // 正常逻辑...
}
```

### 22.4 面试要点

- 降级 vs 熔断：降级是功能替换，熔断是快速失败
- 降级的层次：功能降级（关闭非核心功能）→ 服务降级（跳过不可用服务）→ 数据降级（返回缓存或默认值）
- 设计原则：核心流程尽量少依赖外部服务，外部服务都用 Optional/@Nullable 包装

## 23. LLM-as-Judge 评测模式

### 23.1 核心概念

LLM-as-Judge 是使用 LLM 作为评判者，评估 AI 系统输出质量的方法。它替代了传统的人工评估，实现自动化、可扩展的质量评估。

### 23.2 工作原理

```
待评估的答案 + 评分标准 → LLM → 评分 + 理由
```

**关键设计**：
- 明确的评分标准（0-100 分）
- 要求只输出分数，减少 LLM 自由发挥
- 分数解析支持纯数字和文本中提取数字

### 23.3 EduMate 的三个评估维度

| 维度 | Prompt 设计 | 评估重点 |
|------|------------|---------|
| Answer Relevance | "评估以下答案与问题的相关性" | 答案是否切题 |
| Faithfulness | "评估答案是否忠实于提供的上下文" | 答案是否编造了上下文不存在的信息 |
| Context Relevance | "评估检索到的上下文与问题的相关性" | 检索质量 |

### 23.4 面试要点

- LLM-as-Judge 的可靠性：LLM 自身有偏见（如位置偏见、长度偏见），需要校准
- 提高可靠性的方法：多次评估取平均、使用多个 LLM 交叉验证、与人工评估对比
- 局限性：对主观性强的指标（如创造性、幽默感）评估不准确

## 24. Few-shot Prompt 工程

### 24.1 核心概念

Few-shot Prompting 是在 Prompt 中提供少量示例（通常是 2-5 个），让 LLM 通过类比学习来完成任务的提示工程技术。

### 24.2 示例对比

**Zero-shot（无示例）**：
```
将以下句子分类为正面或负面： "这个产品太棒了"
```

**Few-shot（有示例）**：
```
将以下句子分类为正面或负面：
示例1: "我很喜欢这个" → 正面
示例2: "太失望了" → 负面
示例3: "还行吧" → 中性
现在分类: "这个产品太棒了" →
```

### 24.3 EduMate 中的应用

**意图分类**：
```
示例：
"红黑树的特点" → COURSE_QA
"帮我出5道题" → QUIZ_GENERATION
"什么是B+树" → CONCEPT_EXPLANATION
```

**知识抽取**：
```
输出格式：
[
  {
    "name": "知识点名称",
    "description": "知识点描述",
    "relations": [
      {"type": "PREREQUISITE", "targetName": "目标知识点名称", "description": "关系描述"}
    ]
  }
]
```

### 24.4 面试要点

- Few-shot vs Fine-tuning：Few-shot 不修改模型，成本低；Fine-tuning 效果好但需要数据和计算资源
- 示例选择策略：选择与目标任务最相似的示例、选择多样化的示例
- 示例数量的影响：太少（信息不足）→ 适中（最佳）→ 太多（过拟合、token 浪费）

## 25. Cypher 图查询语言

### 25.1 核心概念

Cypher 是 Neo4j 的**声明式图查询语言**，类似于 SQL 之于关系数据库。它使用 ASCII 艺术风格的模式匹配语法。

### 25.2 基本语法

```cypher
-- 节点用 () 表示，关系用 [] 表示
-- (a)-[r]->(b) 表示从 a 到 b 的有向关系

-- 创建节点
CREATE (k:KnowledgePoint {name: '红黑树', description: '...'})

-- 查询节点
MATCH (k:KnowledgePoint) WHERE k.name = '红黑树' RETURN k

-- 创建关系
MATCH (a:KnowledgePoint {name: '二叉查找树'})
MATCH (b:KnowledgePoint {name: '红黑树'})
MERGE (a)-[:PREREQUISITE]->(b)

-- 多跳查询
MATCH (k:KnowledgePoint {name: '红黑树'})-[r*1..2]-(related)
RETURN k, r, related

-- 最短路径
MATCH path = shortestPath((a)-[*]-(b))
WHERE a.name = '数组' AND b.name = '红黑树'
RETURN path
```

### 25.3 EduMate 中的 Cypher

```cypher
-- 模糊匹配知识点，双向 1 跳遍历
MATCH (k:KnowledgePoint) WHERE k.name CONTAINS $query
OPTIONAL MATCH (k)-[r]->(related:KnowledgePoint)
WHERE type(r) IN ['PREREQUISITE', 'SUCCESSOR', 'RELATED_TO', 'APPLIED_IN']
RETURN k, r, related

UNION

MATCH (related:KnowledgePoint)-[r]->(k:KnowledgePoint)
WHERE k.name CONTAINS $query
RETURN k, r, related
```

### 25.4 面试要点

- Cypher vs SQL：Cypher 天然支持图遍历（多跳），SQL 需要多次 JOIN
- MERGE vs CREATE：MERGE 是 "get or create"（幂等），CREATE 每次创建新节点
- 图遍历的性能优化：使用索引（如 `CREATE INDEX FOR (k:KnowledgePoint) ON (k.name)`），限制遍历深度

## 26. LLM 知识抽取

### 26.1 核心概念

知识抽取是从非结构化文本中自动提取结构化知识（实体 + 关系）的过程，是构建知识图谱的核心步骤。

### 26.2 传统方法 vs LLM 方法

| 方法 | 优点 | 缺点 |
|------|------|------|
| **规则匹配**（正则、模板） | 精确、快速、可解释 | 覆盖面窄、维护成本高 |
| **NER + 关系抽取**（BERT 等） | 覆盖面广 | 需要标注数据、训练成本高 |
| **LLM 抽取**（Few-shot） | 灵活、无需训练数据、可处理复杂语义 | 成本较高、结果不稳定 |

### 26.3 EduMate 实现

`KnowledgeExtractionService` 使用 LLM 逐块抽取：

```java
private static final String EXTRACTION_PROMPT = """
    你是一个课程知识图谱构建专家。请从以下课程文档内容中提取所有知识点及其关系。

    ## 提取规则
    1. 每个知识点必须有 name 和 description
    2. 关系类型包括：PREREQUISITE、SUCCESSOR、RELATED_TO、BELONGS_TO、APPLIED_IN
    3. 只提取文档中明确提到的知识点，不要编造
    4. 输出严格 JSON 数组格式

    ## 文档内容
    课程：%s
    章节：%s
    内容：
    %s

    ## 输出格式
    [
      {
        "name": "知识点名称",
        "description": "知识点描述",
        "relations": [
          {"type": "PREREQUISITE", "targetName": "目标知识点名称", "description": "关系描述"}
        ]
      }
    ]
    """;
```

### 26.4 抽取流程

```
文档分块 → 逐块调用 LLM 抽取 → 解析 JSON → 去重（按 name）→ 存入 Neo4j
```

**去重策略**：使用 `Set<String> seenNames` 按知识点名称去重，先出现的保留。

### 26.5 面试要点

- 知识抽取的挑战：实体歧义（同一实体不同名称）、关系缺失（LLM 漏抽取）、幻觉（LLM 编造不存在的知识点）
- 提高抽取质量的方法：Few-shot 示例、输出格式约束（JSON）、后处理验证
- 知识抽取的批处理：逐块抽取 → 全局去重 → 关系合并
